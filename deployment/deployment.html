02 Architecture as deployed

request path
Browser
   │  https / wss
   ▼
Caddy :443  ── automatic Let's Encrypt cert, websocket-aware
   │
   ├─ /_event*, /_upload*, /ping, /_health, /_all_routes, /auth-codespace
   │     └──► reverse_proxy 127.0.0.1:8000
   │             reflex run --env prod --backend-only   (granian ASGI, systemd)
   │
   └─ everything else
         └──► file_server  /var/www/idatasight
                 static SPA from  reflex export --no-ssr
                 try_files {path} {path}/index.html {path}.html /index.html
Key decision

Caddy serves the frontend as static files; no Node process runs in production. reflex export --frontend-only --no-ssr emits a pure SPA, and the backend runs --backend-only. Instant restarts, ~200 MB less RAM, one less moving part. The cost is that a UI change requires an explicit rebuild step.

Ports: only 22 (from the deployer's IP), 80, and 443 were open. 3000 and 8000 were never exposed — Caddy reaches the backend over loopback.

05 What actually happened

  1. Inspected the repo rather than assuming. Reflex 0.9.8, Python 3.12, uv, bun 1.3.11, no git repo, .web at 217 MB, data/ at 1 MB.
  2. Read warehouse.py and hooks.py — found the Snowflake browser-OAuth problem, and that dispatch() already offloads blocking work via asyncio.to_thread, so no async fix was needed.
  3. Wrote a 3-path decision doc (EC2+Caddy / Cloudflare Tunnel / Reflex Cloud); recommended EC2 because local disk had to persist.
  4. Wrote the automation — five scripts, all syntax-checked.
  5. Tested the frontend export locally before deploying. This caught the REFLEX_API_URL bug that would otherwise have shipped a dead app.
  6. Corrected scripts and runbook for the three build-related findings.
  7. User configured credentials. First attempt failed — account ID pasted into the access-key field. Fixed on the second.
  8. Deploy run #1 — key pair, SG, instance, EIP provisioned. Reached the DNS gate, printed the A record, timed out after 10 minutes.
  9. GoDaddy rejected the record with "Invalid data provided for record data." Diagnosed extensively; never resolved.
  10. Pivoted to sslip.io — wildcard DNS requiring zero configuration.
  11. Deploy run #2 — failed at rsync; macOS ships rsync 2.6.9.
  12. Deploy run #3 — completed. Live, with a genuine Let's Encrypt certificate.
  13. Verified independently, not trusting the script's own health check.
  14. Teardown — all resources destroyed, all billing stopped, audited.

06 Problems encountered

06.1  REFLEX_API_URL, not API_URL — the most dangerous one

Would have silently shipped a non-functional demo

Reflex's own self-hosting documentation says API_URL. On Reflex 0.9.8 that is silently ignored — the env-var prefix on 0.9.x is REFLEX_.

The value is compiled at build time into .web/build/client/assets/reflex-env-*.js as the websocket origin. With the wrong variable it stays ws://localhost:8000/_event, and the deployed page renders perfectly while responding to nothing — no error in the UI, none in the logs.

proof · run against the project venv
API_URL=https://probe.test         → api_url = http://localhost:8000   (ignored)
REFLEX_API_URL=https://probe.test  → api_url = https://probe.test      (works)

Fix: export both REFLEX_API_URL and REFLEX_DEPLOY_URL before building; https:// is auto-upgraded to wss://. Guard added: deploy.sh and redeploy.sh --frontend grep the built bundle for wss://$DOMAIN/_event and abort on mismatch.

06.2  Build output moved in Reflex 0.9

Reflex 0.9 uses React Router + Vite. Output is .web/build/client, not the .web/_static older docs describe. It is also a true SPA — only index.html and 404.html, no per-route HTML — so a deep link to /analysis would 404 without a try_files fallback.

Excluded from rsyncReason
.web217 MB of macOS-built artifacts; breaks on Linux; rebuilt server-side
.venv60 MB of macOS wheels
.statespickled local session state, meaningless remotely
reflex.lockbun lockfile resolved against macOS
data (redeploy only)protects live demo state from being overwritten

data/ is included on first deploy — it carries the seed warehouse panels, concept definitions, and ledger.json. The app is useless without it.

06.3  Snowflake cannot work headless — and fails silently

warehouse.py:234 · then :250
conn = snowflake.connector.connect(connection_name=SF_CONNECTION)  # "MN74135"

# ...
except Exception as e:
    print(f"[warehouse] snowflake read failed for {ds_id}: {e}; using CSV")

The connection profile uses browser OAuth. A headless server has no browser, so connect throws — and the handler catches every exception and falls back to the CSV mirror. The UI is byte-identical either way. You cannot tell from the screen whether Snowflake is being used.

Decision — ship on CSV deliberately

data/warehouse/ holds the same panels; warehouse.py treats the sources as interchangeable by design. The demo is identical while an entire class of silent failure disappears. Snowflake was deferred to enable-snowflake.sh (RSA key-pair auth), written and syntax-checked but never run.

if enabling later · verify with the log, not the screen
journalctl -u idatasight --since '2 min ago' | grep -i 'snowflake read failed'
# silence = success

Also check Snowflake's network-policy IP allowlist — it blocks with the same invisible symptom.

06.4  EverOS — resolved differently than assumed

At deploy time nothing in the tree referenced EverOS. The role it was described as playing — a module needing local disk — was filled by data/, specifically data/store/ledger.json, which ledger_store.py appends to on every analysis run. That persistence requirement is what ruled out Reflex Cloud's ephemeral filesystem and drove the EC2 choice.

Known gap — fix before any EverOS deploy

The systemd unit set a placeholder EVEROS_DATA_DIR=/home/ubuntu/idatasight/data/everos. The project's actual convention is EVEROS_ROOT, with a storage root at ~/.everos. The placeholder name is wrong, and the real default sits outside the app directory — therefore outside every backup path this deployment used. Set EVEROS_ROOT explicitly to a persistent path and confirm the process user owns it.

06.5  AWS credential paste error

First sts get-caller-identity returned InvalidClientTokenId. Diagnosis without printing secrets — inspect the shape:

shape check
access_key_id : len 12, prefix 7897     ← wrong
secret_key    : len 40                  ← correct

An AWS access key ID is 20 characters beginning AKIA (or ASIA for temporary credentials, which also need a session token). A 12-digit number is an account ID — and the account did turn out to be 789748176365. Lesson: validate credential shape before blaming permissions. Length and prefix identify the error instantly and leak nothing.

06.6  GoDaddy — UNRESOLVED

Blocked the intended domain · never solved

Submitted A / idatasight / 54.71.45.186 / TTL 1 Hour — confirmed correct by screenshot. GoDaddy returned "Invalid data provided for record data."

Ruled out by direct queries against GoDaddy's authoritative nameserver (ns69.domaincontrol.com), bypassing all caching:

Duplicate A recorddig A idatasight… @ns69empty — name free

Conflicting AAAA / TXTdig AAAA/TXT … @ns69empty
Doubled-domain typodig A …com.consciouselectron.comempty

Value malformedscreenshot54.71.45.186 — correct
Propagation delayauthoritative NS queryrecord never saved at all

Untested hypotheses, most plausible first:

  • Domain Connect / third-party zone management. The apex resolves to 76.223.105.230 and 13.248.243.5 — AWS Global Accelerator IPs, typical of an Amplify custom domain. If configured via GoDaddy's Domain Connect integration, GoDaddy can reject manual record edits with exactly this generic error. Leading candidate.
  • Invisible characters from pasting into the Name or Value field.
  • Stale CSRF / session state — the form had been open a long time.
  • Browser extension interfering with the request.
If revisiting

Check whether the zone is under Domain Connect management (GoDaddy DNS page → look for a third-party "connected" banner), or use GoDaddy's DNS API, which returns far more specific errors than the web form.

06.7  macOS ships rsync 2.6.9

deploy run #2
rsync: unrecognized option `--info=stats1'

macOS ships openrsync / rsync 2.6.9-compatible, predating --info= (rsync 3.1, 2013). Lesson: deploy scripts running from macOS cannot assume GNU userland — the same applies to sed -i, date, and timeout, which is absent entirely and bit us once during local testing.

06.8  sslip.io — the unblock

With GoDaddy refusing, sslip.io provided wildcard DNS requiring zero configuration: <ip>.sslip.io resolves to <ip>. Because it is on the Public Suffix List, Let's Encrypt treats each IP-subdomain as its own registered domain, so a genuine certificate is issued — no browser warning, nothing to explain to judges. Live in ~6 minutes.

06.9  DNS gate timeout too short

The initial 10-minute poll was tuned for propagation delay, not for a human fighting a web form. Raised to 25 minutes, and taught to detect the doubled-domain typo immediately rather than burning the whole window.

06.10  Teardown data rescue failed — cause not diagnosed

teardown.sh attempts to pull data/ down before destroying anything. It reported could not reach instance, skipping and left a 0-byte deploy/data-backup.tgz. The rescue is correctly ordered before termination, so ordering was not the cause; SSH failed for a reason that could not be investigated afterwards, the instance being gone.

Impact: minimal. Local data/ was never touched — deploys only ever pushed it upward and redeploy.sh excludes it. The only loss was demo-session state generated on the instance.

fix for next time
[ -s "$HERE/data-backup.tgz" ] || { echo "backup empty — aborting"; exit 1; }
Lesson

A backup step that fails soft is not a backup. Verify the artifact is non-empty before the irreversible action.

Two verification traps worth recording

"Invalid transport" on a socket.io polling probe is expected, not a fault — Reflex is configured websocket-only, so it correctly rejects polling. The reply itself proves the backend is reachable through Caddy.

HTTP/2 returns 400 for a websocket upgrade. Connection: Upgrade is invalid in HTTP/2, so the test must force --http1.1 or it is meaningless. The first attempt looked like a failure and was purely a test artifact.

08 Lessons learned

  1. Test the risky build step locally before provisioning anything.

    Running reflex export on the laptop cost 3 minutes and caught the REFLEX_API_URL bug. Discovering it on the server mid-hackathon would have cost far more — and it presents as a working-looking app, the hardest failure to diagnose.

  2. Verify, don't trust — especially anything compiled at build time.

    Every build-time-baked value deserves an assertion. Grepping the bundle is cheap insurance against the worst failure mode.

  3. Silent fallbacks are worse than crashes.

    Two independent instances here: Snowflake falling back to CSV, and the wrong env var falling back to localhost. Both produce a healthy-looking system. Where a fallback exists, find the signal that distinguishes the paths and check that.

  4. Library docs go stale; the installed version is the truth.

    The Reflex blog said API_URL; the installed 0.9.8 required REFLEX_API_URL. Two minutes of introspection beat the documentation.

  5. Diagnose credentials by shape, not by retrying.

    Length and prefix identified the account-ID-in-key-field error immediately, without printing or transmitting a secret.

  6. Query authoritative nameservers when debugging DNS.

    dig @ns69.domaincontrol.com separated "not saved" from "not propagated" instantly — which redirected the entire GoDaddy investigation.

  7. Have an escape hatch that removes the blocking dependency entirely.

    sslip.io eliminated DNS from the critical path. Under time pressure, an unblock that sidesteps the problem beats continuing to fight it — and the real domain was always one config line away.

  8. Make deploy scripts idempotent and resumable from the start.

    deploy.sh ran four times. Because completed steps were recorded in deploy/.state, three retries cost seconds instead of full re-provisions.

  9. A backup that fails soft is not a backup.

    The teardown rescue silently produced a 0-byte file and proceeded to destroy the source. Assert the artifact before the irreversible step.

  10. Don't assume GNU userland on macOS.

    rsync --info, timeout, and sed -i all differ or are absent.

  11. Ask which failure actually matters.

    Rather than making the demo "correct" by wiring up live Snowflake, the right call was CSV — identical output, one less silent failure mode, six minutes saved for rehearsal.

10 Teardown & audit

post-teardown · every billable resource class in the region
aws ec2 describe-instances  --query 'Reservations[].Instances[?State.Name!=`terminated`]'
aws ec2 describe-addresses                    # Elastic IPs
aws ec2 describe-volumes                      # orphaned EBS
aws ec2 describe-snapshots --owner-ids self

All four returned empty. Key pair and security group deleted.

Do not stop at "the instance is terminated"

Orphaned EBS volumes and released-but-still-allocated Elastic IPs are the classic silent charges. Audit all four resource classes.

11 Redeploying

Everything in deploy/ is intact and reusable. A fresh run creates a new instance and new Elastic IP, so any sslip.io URL will differ. Nothing needs cleaning up first.

from scratch
# 1. credentials — your own terminal, keeps secrets out of any transcript
aws configure --profile idatasight

# 2. set DOMAIN in deploy/config.env
#    sslip.io needs the IP, known only after provisioning — so either start
#    with the real domain, or deploy once, read the IP, then switch.

# 3.
./deploy/deploy.sh
iteration loop
./deploy/redeploy.sh              # ~40 s — handler bodies, backend/*.py
./deploy/redeploy.sh --frontend   # ~4 min — components, pages, theme,
                                  #          or any added/renamed State var

When unsure, use --frontend. A skipped rebuild serves a stale UI, which looks exactly like the fix silently failing.
